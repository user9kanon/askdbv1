     AskDB v1 — implementation plan as thin vertical slices

     Context

     The repo has only the scaffold: CLAUDE.md, docs/SPEC.md, docs/one-pager.md,
     .env.example and the CloudMetrics fixtures in test/. There is no src/,
     tests/, pyproject.toml or docs/PLAN.md yet. This plan breaks SPEC v1 into 8
     slices, done in order. Each slice can be tested end to end on its own and
     fits in one short session. When implementation starts, slice 1 writes this
     plan into docs/PLAN.md, and later slices tick items off there, as CLAUDE.md
     requires.

     Ordering principle: the safety boundary (G2/G3: scope copies and the
     read-only executor) comes before any LLM or UI work. Every later slice is
     then built on the real enforcement path, never on a stub.

     ---

     Slice 1 — Project skeleton + strict config loading

     Goal: uv run askdb validate-config loads ASKDB_DATABASE_CONFIG, validates
     it strictly and exits non-zero on any error (§4.2, §11.4).
     - Pydantic models with extra="forbid"; ${VAR} expansion in path (an unset
       variable is an error); safe YAML loader.
     - Cross-checks against the source DB, opened read-only: every table and
       column exists, access coverage (each table in exactly one bucket),
       via→references→PK chains with cycle detection (multi-hop), sensitive
       categories declared, at most one display_name per table and only on
       tables with a PK, and every metric sql/breakdown_sql runs (with dummy
       :start/:end and an empty {{filters}}).
     - Validation-dataset model (§4.3), loaded only by tests.
     - A second synthetic config + DB for tests (order_items → orders → 
       customers, a different scoping column, no metrics).

     Files: pyproject.toml, src/askdb/__init__.py, src/askdb/cli.py,
     src/askdb/config/{models,loader,validate}.py, src/askdb/evalset.py,
     tests/conftest.py, tests/unit/test_config_*.py, tests/fixtures/synthetic/
     (built by a conftest fixture), docs/PLAN.md.
     Verify: uv run pytest tests/unit covers the CloudMetrics config passing,
     the synthetic config passing, and one failing case per rule (unknown key,
     typo in access, missing column, cycle, bad via, broken metric SQL, unset
     env var). uv run askdb validate-config exits 0 with the dev env. Ruff is
     clean.
     Depends on: none.

     Slice 2 — Scope builder + read-only executor (the G2/G3 boundary)

     Goal: given a grant (groups or All, plus sensitive categories), build
     var/scopes/<id>.db and run SQL against it safely (§6.2, §7.2).
     - Scope id = hash(grant, group map, source DB hash, config hash).
     - Builder: filter row_scope.table, then scoped_tables parent-first
       (dropping NULL or orphaned via rows), copy reference_tables whole,
       include listed columns only, drop ungranted sensitive columns. Write to a
       temp path, verify row counts and FKs, rename atomically and set the file
       read-only. Compute data_coverage start/end.
     - Executor: mode=ro URI, PRAGMA query_only=ON, an authorizer allowlist
       (SELECT/READ/allowlisted FUNCTION/RECURSIVE), single-statement check
       (sqlglot), rejection of 'now'/CURRENT_*, a 5 s progress-handler timeout,
       and a 10,000-row cap.
     - Per-scope DDL renderer (table and column descriptions as comments;
       omitted columns never mentioned).
     - CLI: askdb build-scope --groups EMEA --sensitive customer_identity for
       manual inspection.

     Files: src/askdb/scopes/{builder,ids}.py, src/askdb/executor.py,
     src/askdb/ddl.py, tests/redteam/test_scope_integrity.py,
     tests/redteam/test_executor_attacks.py, tests/unit/test_scope_builder.py,
     tests/unit/test_ddl.py.
     Verify: red-team tests inspect scope files directly (EMEA file holds only
     EMEA countries, no company_name without the grant, multi-hop on the
     synthetic DB). Executor attacks are all denied: ATTACH of another scope or
     the source, PRAGMA, INSERT/UPDATE/DELETE/DROP, multiple statements,
     load_extension, date('now'), and a runaway recursive CTE hitting the
     timeout. The DDL for a restricted scope never contains the dropped column
     name.
     Depends on: 1.

     Slice 3 — App DB, auth, grants, and a signed-in Ask page shell

     Goal: uv run askdb serve on 127.0.0.1. Users log in, get the scope tied to
     their grant, and see an Ask page, or the "no access yet" page (§2, §3.4,
     §7.1, §13).
     - var/app.db schema and migrations for users, grants, scope_groups (seeded
       from config), scopes, access_requests, audit_log and settings.
     - argon2 hashing, signed HttpOnly SameSite=Strict session cookie, CSRF
       tokens, forced password change on first login.
     - askdb create-admin, askdb seed-demo (EMEA manager, All-regions exec with
       identity, admin, a no-grant user).
     - Startup: validate config, seed groups, build scopes for existing grants.
       A user whose scope isn't ready sees "Your access is being updated". Audit
       login and scope-build events.
     - The Ask page is a template with a question box and a scope label ("EMEA
       only (your access)"). Request access notifies admins (an access_requests
       row).

     Files: src/askdb/app.py, src/askdb/db/{schema,repo}.py, src/askdb/auth.py,
     src/askdb/grants.py, src/askdb/audit.py,
     src/askdb/templates/{base,login,ask,no_access}.html, src/askdb/static/,
     tests/unit/test_auth.py, tests/unit/test_grants.py,
     tests/redteam/test_cross_user_scope.py.
     Verify: FastAPI TestClient tests cover login and logout, CSRF rejection, a
     must-change-password redirect, the no-grant page, the bind address fixed to
     127.0.0.1, and that each demo user resolves to the correct scope file.
     Manual check: seed-demo, then serve, then log in as the EMEA manager.
     Depends on: 2.

     Slice 4 — First answer: certified metric, explicit period, answer card

     Goal: "What was revenue in Q3 2025?" returns a headline, an interpretation
     line, a scope label and a trend chart, end to end through the real LLM
     (§5.1 explicit periods, §5.4, §6.1, §8.2).
     - Period resolver: explicit quarter/year/month with fiscal start, half-open
       ranges, coverage clipping ("data through Nov 15 only"), "No data for
       this period — data covers…", and snapshot metrics "as of latest data".
     - Interpreter (one pass for now): prompt = description + scope DDL + metric
       catalog + calendar + coverage + today, with structured output via tool
       use. Output is validated (unknown metric or filter rejected).
     - Certified execution: {{filters}} substitution with bound :f_<name>
       values, trend runs per trend grain, breakdown_sql for snapshots.
     - Sanity checks (§6.3): no rows or NULL means "No data found", the
       anomalous-zero banner, and static-snapshot freshness wording.
     - Answer card partial via HTMX, Chart.js (selected period highlighted,
       partial period hatched, text alternative), unit formatting. Audit row per
       question (no result values).
     - An injectable LLM client, so tests use a recorded or fake client. Load
       the claude-api skill before writing the client.

     Files: src/askdb/periods.py, src/askdb/llm/{client,prompts,schema}.py,
     src/askdb/pipeline.py, src/askdb/metrics.py, src/askdb/sanity.py,
     src/askdb/format.py, src/askdb/templates/answer_card.html,
     tests/unit/test_periods.py, tests/unit/test_filters_substitution.py,
     tests/unit/test_metrics_eval_agreement.py,
     tests/unit/test_pipeline_certified.py.
     Verify: unit tests cover period edges and fiscal start, binding-only filter
     substitution, and metric/eval agreement for the §4.4 list (mrr, arpu,
     active_customers, avg_resolution_hours, churn_rate Q3 2025, revenue 2025,
     mrr_by_plan). A pipeline test with a fake LLM checks that EMEA and All
     users get different numbers for the same question with correct labels. A
     manual check in the browser uses the real API.
     Depends on: 3.

     Slice 5 — Uncertainty: clarify and decline (G1)

     Goal: AskDB asks or declines instead of guessing (§5.1–5.3, §5.5, §8.3).
     - Pre-checks before the LLM: grant, English, daily question limit (setting,
       default 200; usage table).
     - Interpret ×2 and compare (metric, period, filters). A difference triggers
       clarification.
     - Chips: relative phrases in static_snapshot mode, vague phrases in both
       modes, no period on a period metric, multiple metric matches, and "None
       of these" leading to "Try rephrasing" plus Flag.
     - Declines: small talk, write requests, injection or system-prompt
       requests, follow-ups, forecasts, exports, non-English, and past or trend
       snapshot questions (with a [Show current X] chip). A decline produces no
       SQL.
     - Filter value index read from the user's scope copy: fuzzy matching, zero
       or many matches lead to chips, duplicate display_name values lead to one
       chip per row with differing details plus "All named X combined", and the
       chosen chip filters on the PK.
     - Chip clicks resubmit a resolved query (no extra LLM call).

     Files: src/askdb/precheck.py, src/askdb/clarify.py,
     src/askdb/value_index.py, src/askdb/pipeline.py, src/askdb/llm/prompts.py,
     src/askdb/templates/{clarify,refusal}.html, tests/ambiguity/test_*.py,
     tests/redteam/test_chip_leakage.py, tests/unit/test_value_index.py.
     Verify: the ambiguity suite (live LLM, gated by ANTHROPIC_API_KEY) covers
     "last month" with an injected today, "recently", "MRR at end of 2024",
     duplicate "Acme"-style names, small talk, "mark invoices paid" and "ignore
     previous instructions". The false-confident rate is 0, and declines leave
     no SQL in the audit log. Red-team: an EMEA user never sees non-EMEA values
     in chips. Unit tests run with a fake LLM to check the compare logic and
     chip construction.
     Depends on: 4.

     Slice 6 — Fallback SQL, comparator, restricted questions, validation suite

     Goal: answer uncertified questions safely and pass the 29-case eval (§6.2
     fallback, §7.4, §8.2 duplicates, §11.2).
     - Fallback: two independent LLM SQL candidates. Each goes through the
       slice-2 executor plus fallback rules (no SELECT *, non-aggregate queries
       need LIMIT). If the results differ, return "I'm not confident about this
       one" with a flag option. Uncertified banner and a result table.
     - Result-set comparator (§11.2): one-to-one column mapping by value
       multisets, exact row multiset, ORDER BY via sqlglot with ties allowed,
       LIMIT tie blocks, 1e-6 float tolerance, NULL = NULL. One shared module is
       used by the fallback agreement check and the eval harness.
     - Restricted questions: "Customer names require Customer identity access",
       never IDs silently.
     - Duplicate-label display: append "(#key)" to colliding names only; show a
       note when no key column is present.
     - Validation harness: runs as an All + all-sensitive user, skips
       conversation cases with a reason, and fails if declined cases produce
       SQL.

     Files: src/askdb/fallback.py, src/askdb/compare.py, src/askdb/pipeline.py,
     src/askdb/templates/answer_card.html, tests/unit/test_compare.py,
     tests/validation/test_eval_set.py, tests/ambiguity/test_restricted.py,
     tests/redteam/test_prompt_injection_sql.py.
     Verify: comparator unit tests cover superset columns, reordered and renamed
     columns, ORDER BY ties, LIMIT ties and float tolerance. uv run pytest 
     tests/validation passes all 28 non-skipped cases and reports 1 skipped. A
     user without identity access asking "top 10 customers by name" gets the
     restriction message.
     Depends on: 5.

     Slice 7 — Cache, pins, dashboards, metric drift

     Goal: users pin certified answers, build personal dashboards, and get
     cached re-runs (§6.4, §9.1, §9.3).
     - Result cache keyed on user + resolved query + scope file hash. It is
       invalidated by a rebuild, a grant change or a metric hash change, and
       hits are still audited.
     - A pin stores the resolved query (metric, bound filters, relative-to-data
       or explicit period) and re-runs with no LLM. Dashboards are named,
       ordered and personal.
     - metric_versions table: on config load, compare SQL hashes. Changed
       metrics show "Definition changed on <date>"; removed metrics show a
       broken state and notify the owner.
     - After a grant change, pins re-run in the new scope with updated labels.

     Files: src/askdb/cache.py, src/askdb/pins.py, src/askdb/drift.py,
     src/askdb/templates/{dashboard,dashboards}.html, tests/unit/test_cache.py,
     tests/unit/test_pins.py, tests/unit/test_drift.py,
     tests/redteam/test_cache_isolation.py.
     Verify: EMEA and All users asking the same question never share a cache
     entry. A pin re-run makes no LLM call (fake client asserts it is never
     called). A grant change gives the pin a new scope label and value. Editing
     a metric's SQL in a temp config produces the drift notice.
     Depends on: 6 (pins are certified-only; slice 4 is the minimum, but 6
     settles the answer-card shape).

     Slice 8 — Scheduled reports + admin console

     Goal: complete v1: scheduled snapshots delivered to an in-app inbox, and
     the full admin console (§8.4, §9.2, §10).
     - APScheduler in-process. Daily, weekly or monthly in the user's time zone,
       run against the user's current scope. Each run stores a snapshot and
       posts a link to the Reports inbox (optional email over SMTP, link only).
       Failures are shown in the report. Disabled users' schedules pause and
       their snapshots are deleted.
     - Admin console: users (create with a one-time password, disable, reset),
       grants (groups or All, sensitive categories) with an audit before/after
       diff, which triggers a rebuild. Also: scope-group map editor with an
       unmapped-values warning, read-only config view with drift history,
       settings (daily limit, timeouts, SMTP), review queue ("This looks wrong"
       flags plus fallback questions grouped by frequency), access requests, and
       a searchable audit log. Audit retention is 1 year.
     - Rebuild triggers: group map or grant edits, and changes to the source DB
       or config hash.

     Files: src/askdb/scheduler.py, src/askdb/reports.py,
     src/askdb/admin/{routes,forms}.py, src/askdb/templates/admin/*.html,
     src/askdb/templates/reports.html, tests/unit/test_scheduler.py,
     tests/unit/test_admin.py, tests/redteam/test_scheduled_scope.py,
     tests/redteam/test_admin_authz.py.
     Verify: a scheduled run (triggered directly in the test) produces a
     snapshot built from exactly the user's scope, and narrowing the grant
     narrows the next run. Non-admins get 403 on every admin route. Grant edits
     are audited with a diff and rebuild the scope. Full uv run pytest plus lint
     pass, and the validation, ambiguity and redteam suites are green (§11
     release gate). Manual demo: log in as each seeded user and compare the
     answers.
     Depends on: 7.
